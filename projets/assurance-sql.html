Une clé composite pour résoudre un problème d'identifiant

Modéliser une base de données ne se résume pas à dessiner des tables : c'est d'abord choisir la bonne clé. Sur ce projet d'assurance habitation, le code postal ne suffisait pas à identifier une commune. Voici comment le schéma, le chargement et les douze requêtes SQL qui en découlent ont été construits.

Le contexte et le besoin métier

Un assureur habitation dispose de deux fichiers, ses contrats d'un côté, un référentiel géographique des communes françaises de l'autre, sans base de données pour les exploiter ensemble. L'exercice couvre le cycle complet d'un premier projet SQL : comprendre les données, concevoir un schéma normalisé, créer et charger la base, puis répondre à douze questions métier concrètes.

Les données : sources, qualité, limites

Deux fichiers sources : les contrats (adresse, surface, type de bien, formule de garantie, cotisation) et un référentiel par commune (région, département, académie). Comprendre les données avant de les modéliser a commencé par un dictionnaire complet, colonne par colonne, avec type, taille et description, avant toute création de table.

Pourquoi le code postal ne suffit pas comme clé. Un même code postal peut couvrir plusieurs communes, ce n'est donc pas un identifiant fiable pour relier deux tables. La clé retenue, Code_dep_code_commune, concatène le code département et le code commune : une clé composite construite spécifiquement pour être unique, plutôt qu'une donnée déjà présente mais ambiguë.

Cette clé a aussi révélé un vrai problème de données : sur 30 335 contrats sources, 9 pointent vers un code de commune absent du référentiel région, tous situés en outre-mer. Plutôt que de les forcer dans la base ou de les écarter en silence, l'écart est identifié et quantifié : 30 326 contrats chargés, 9 orphelins documentés.

La démarche

Le schéma relationnel suit directement le dictionnaire de données : deux tables, une relation 1-N de région vers contrat, une seule clé étrangère. Modélisé avec SQL Power Architect, il génère le script de création des tables, avec la clé primaire de chaque table et la contrainte de clé étrangère explicitement posées avant tout chargement.

Chaque requête suit la même méthode : reformuler la question métier avec précision, identifier les tables et colonnes réellement nécessaires, choisir la bonne fonction SQL, puis vérifier que le résultat répond effectivement à la question posée, pas seulement qu'il s'exécute sans erreur. Sur la requête 2, par exemple, la table région contient une ligne par commune : lister les noms de région sans DISTINCT aurait produit des dizaines de répétitions du même nom. La logique se documente aussi bien qu'elle se code.

Les résultats et l'impact

25 612 des 30 326 contrats chargés portent sur une résidence principale. La cotisation mensuelle moyenne s'établit à 19,33 €, mais avec un écart net selon le territoire : 36,40 € à Paris contre 17,07 € en Corse-du-Sud, dixième département du classement. La concentration géographique est plus marquée encore : l'Île-de-France rassemble 14 177 contrats, près de 47 % de l'ensemble du portefeuille, loin devant la Provence-Alpes-Côte d'Azur et ses 3 279 contrats.

Le croisement type de bien et localisation affine la lecture : sur le seul département de Saône-et-Loire, quatre contrats concernent des maisons en résidence principale, deux en formule Integral et deux en Classique, un échantillon assez petit pour illustrer qu'une requête bien construite reste utile même sur des volumes réduits, pas seulement sur les gros agrégats.

Les limites et les prochaines pistes

Le schéma actuel ne couvre que deux entités, contrat et région : il ne permet pas encore de suivre l'historique d'un contrat dans le temps, ni de relier un sinistre à un contrat. Les 9 contrats orphelins restent hors base, une perte mineure en volume mais un signal à surveiller si la source de données s'étend à de nouveaux territoires.

Les pistes que je recommande : ajouter une table sinistres reliée à contrat pour croiser cotisation et sinistralité par territoire, et automatiser le contrôle des codes de commune orphelins à chaque nouvel import, plutôt que de le découvrir après coup comme ici.
